# Oscars service

Spring MVC REST, WAR для WildFly. Публичные URL из `oscarApi.yaml` сохранены.

## Выполнение джоб

`POST /oscar/movies/reward-r` и `POST /oscar/movies/reset-oscars-by-genre/{genre}` сохраняют команду в собственном PostgreSQL и возвращают `202` после коммита. Таблица `oscar_job` содержит UUID, тип, JSON-аргументы, статус, результат, ошибку последней попытки, даты, счётчик попыток и срок захвата задания исполнителем.

Каждый публичный POST создаёт новую джобу. Идемпотентность относится к внутренним повторам с одним `jobId`; повтор публичного POST после потери ответа 202 пока не объединяется с первой джобой.

Очередь отображается на JPA-сущность `JobEntity`. `JobRepository` использует `EntityManager`: создание через `persist`, чтение через `find`, выбор доступного задания через Criteria API и обновление состояния управляемой сущности. Аргументы отображаются на `JSONB` средствами Hibernate, без ручной сериализации JSON.

Один планировщик в экземпляре приложения выбирает доступную джобу с `PESSIMISTIC_WRITE` и режимом `SKIP LOCKED`. Выбор и изменение состояния сущности происходят в одной короткой транзакции; Hibernate сохраняет изменения при коммите. HTTP-вызов выполняется после её завершения. После рестарта задания подбираются из БД; просроченный захват можно забрать повторно. Запись результата также блокируется и проверяет `lease_token`, чтобы старый исполнитель не мог перезаписать результат нового. Для сроков захвата используется общее время PostgreSQL.

Spring управляет локальным `EntityManagerFactory` и транзакциями очереди, `open-in-view` отключён, Hibernate проверяет соответствие существующей схеме (`ddl-auto=validate`). В WAR отключена подсистема JPA WildFly, чтобы она не подменяла Hibernate и управление persistence unit приложения.

Вместо загрузки коллекции и множества PUT выполняется один `POST /internal/operations` в Movies. Передаются исходный `jobId`, `type` и `arguments`. Контракт описан в `../internalApi.yaml`. Заголовок `X-Internal-Token` настраивается через `MOVIES_INTERNAL_TOKEN` в обоих сервисах; во фронтенд токен не передаётся.

## Транзакции и повторы

В Movies журнал `movie_operation` хранится в той же БД, что и фильмы. Регистрация команды коммитится отдельно. Выполнение блокирует запись команды и берёт общую транзакционную advisory-блокировку для массовых операций. Изменение фильмов и `COMPLETED` с количеством изменённых строк коммитятся вместе. Повтор завершённой команды возвращает сохранённый результат. Другой тип или жанр с тем же UUID возвращает `409`.

Для JDBC используется отдельный нетранзакционный пул Payara `jdbc/MoviesOperationsDS`: локальной транзакцией и savepoint управляет код, без JTA. Перед bulk UPDATE создаётся savepoint. При ошибке SQL изменения фильмов откатываются до него, а запись ошибки попытки сохраняется под всё ещё удерживаемой блокировкой. Ошибка сохранения результата или потерянное подтверждение коммита возвращают `503`; повтор проверит реальный результат по исходному ID.

Общий кэш JPA в Movies отключён: изменения через JDBC сразу видны при последующем чтении фильмов через JPA, в том числе на других экземплярах сервиса.

* Неверные аргументы и переполнение `BIGINT` — окончательная ошибка; переполнение откатывает весь bulk UPDATE.
* Таймаут SQL, deadlock и serialization failure — повторяемые ошибки. По умолчанию Movies допускает 8 выполненных попыток, после чего сохраняет `FAILED / RETRIES_EXHAUSTED`.
* Ошибки сети, HTTP 408/429/5xx, пустой или некорректный ответ — результат не подтверждён. Oscars повторяет запрос с тем же ID с экспоненциальной задержкой и случайным разбросом: от 0,5–1 секунды до 30–60 секунд. На сетевые повторы конечный лимит не ставится: они не должны превращать неизвестный исход в ложный `FAILED`. HTTP 404 внутреннего маршрута также повторяется: он может появляться, пока Payara ещё разворачивает приложение.
* HTTP 400/401/403/409/422 — окончательный отказ внутреннего API.

Во время ожидания повтора публичный статус остаётся `RUNNING`. У каждого сервиса свои локальные транзакции; распределённой транзакции нет. Статусы могут временно различаться, повторный запрос восстанавливает соответствие.

По умолчанию SQL получает оставшийся бюджет в 5 секунд с начала транзакции выполнения; ожидание блокировки ограничено дополнительно 1 секундой. Это бюджет попытки выполнения, а не обещание получить HTTP-ответ ровно за 5 секунд: регистрация, сохранение результата, rollback и commit требуют времени отдельно. HTTP read timeout — 10 секунд, захват задания — 45 секунд. При настройке оставляйте захват длиннее HTTP timeout и времени записи результата.

Записи `movie_operation` автоматически не удаляются: после удаления записи старый UUID снова мог бы начислить награду. Политика архивирования должна сохранять ключи идемпотентности.

## Развёртывание

Из корня проекта:

```bash
docker compose -f deploy/docker-compose.yml up -d --build
```

Compose создаёт `oscars-postgres` с постоянным volume `oscars-pgdata`. Spring инициализирует таблицу и индекс из `schema.sql`. Сервис `movies-migrate` применяет SQL миграцию журнала в существующую БД Movies, не удаляя фильмы; Payara запускается после успешной миграции. `docker compose down` сохраняет данные, `down -v` удаляет volumes.

Для локальной лабы в Compose заданы значения по умолчанию для БД и внутреннего токена. Их можно заменить через окружение:

| Переменная | Значение по умолчанию |
|---|---|
| `MOVIES_INTERNAL_TOKEN` | `soa-local-internal-token` в Compose; одинаковый в сервисах |
| `MOVIES_OPERATION_TIMEOUT_MS` | `5000` |
| `MOVIES_OPERATION_MAX_ATTEMPTS` | `8` |
| `MOVIES_SERVICE_URL` | `https://payara:8181` |
| `MOVIES_CONNECT_TIMEOUT` / `MOVIES_READ_TIMEOUT` | `3s` / `10s` |
| `OSCARS_DB_URL` | `jdbc:postgresql://oscars-postgres:5432/oscars` |
| `OSCARS_DB_USER` / `OSCARS_DB_PASSWORD` | `oscars` / `oscars` |
| `JOBS_POLL_DELAY` | `1000` миллисекунд |
| `JOBS_LEASE_DURATION` | `45s` |

Проверка публичного API:

```bash
curl --cacert deploy/certs/out/ca.crt -X POST https://localhost:8443/oscar/movies/reward-r
curl --cacert deploy/certs/out/ca.crt https://localhost:8443/oscar/jobs/<job-id>/status
```

После рестарта статус доступен по прежнему ID. Журнал в текущем фронтенде показывает джобы текущей сессии; ранее созданную можно проверить через поле ID операции. Опрос не прерывается по истечении двух минут и восстанавливается после временных сетевых ошибок.

## Сборка и тесты

```bash
mvn clean verify
```

Тесты запускают временный PostgreSQL через Embedded Postgres, без Docker. Проверяются конкурентные дубликаты, потерянное подтверждение коммита, rollback при переполнении и таймауте, восстановление захватов, защита от устаревшего исполнителя, HTTP-классификация ошибок и запуск Spring с JPA. Тесты очереди используют настоящий `EntityManager`, транзакционный Spring-прокси и PostgreSQL; HTTP вызывается после коммита захвата. При первом запуске Maven загружает PostgreSQL binaries; `initdb` требует запуска от обычного пользователя.
